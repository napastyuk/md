Цель — максимально ограничить LLM. Чем больше уточнений, тем лучше результат. Все пункты не обязательны, но их следует выбирать в зависимости от проекта.

## Этап 1. Спецификация
1. Проектирование. Напиши (с помощью llm) спецификацию, в которой опиши цели, задачи, компоненты, входные и выходные данные. Цель — сфокусировать LLM именно на вашей задаче. На этом этапе можно обсудить с LLM стек технологий. 
2. Зафиксируй термины/словарь/ubiquitous language. Цель исключение двусмысленности слов при постановке задач для LLM.
3. Выбираем архитектурный стиль (Clean, Hexagonal, Onion и т.д.) и набор принципов проектирования (SOLID и др.). Цель — зафиксировать в спецификации, что каждый класс решает только одну задачу. Архитектура определяет, какие нужны классы и за какую задачу отвечает каждый из них. По мере принятия архитектурных решений фиксировать их в отдельном документе - ADR (Architecture Decision Record). 
4. Фиксация в спецификации code style.
   - обязательное написание комментариев (JSDoc, docstrings, DocFX и т.д.);
   - указание принципа: «Комментарий должен объяснять не что делает код, а почему он это делает»;
   - Класс должен иметь одну ответственность. Количество методов не более чем нужно для выбранной ответственности;
   - типизация для выбранного языка;
   - соблюдение принципов защитного программирования;
   - спецификация определяет код, а не наоборот. Если есть расхождение, сначала меняем спецификацию.
   - запрет на изменение кода который не относится к задаче. Можно разрешить фиксацию как задачу на будущее.
1. Фиксация в спецификации высокоуровневого Roadmap. Цель — разрабатывать по одной фиче за раз, чтобы между итерациями проект оставался работающим.
2. Финализация спецификации.
   - все предыдущие этапы собираем в Markdown;
   - передаём LLM с ролью аналитика;
   - просим проверить на ошибки;
   - просим сделать спецификацию для разработки ПО.

## Этап 2. Инфраструктура
Разворачиваем пустой проект для выбранного фреймворка или библиотеки. Настраиваем Git, подключение к базе, тестовый стенд. При необходимости подключаем агентские MCP для автоматического запуска проверок. Настраиваем запуск quality gates через CI:
- сборка, проверка корректности подключений модулей;
- тесты;
- линтеры;
- проверка типов;
- автоформатирование;
- автогенерация документации, контрактов (OpenAPI);
- проверка выполнения сетевых контрактов тестами;
- проверка с помощью специализированных навыков (skills) или LLM в роли архитектора-аудитора. Цель — проверить, что код не увеличивает технический долг и соответствует спецификации.

## Этап 3. MVP
Продолжаем работу в подготовленном проекте. В формате agile-спринтов для каждого пункта из Roadmap.
Передаём LLM спецификацию, минимальный необходимый контекст кода и выбранную цель этапа. 
1. Просим LLM составить план на этот этап. Цель та же — чем конкретнее задача, тем лучше результат.
2. Работаем по TDD. Сначала просим написать юнит-тесты, проверяем, что они тестируют именно то, что написано в спецификации, и только после этого просим реализовать функциональность, пока тесты не станут зелёными. Цель — сделать проект устойчивым к любому рефакторингу. Чтобы LLM не внесла нежелательные изменения, достаточно одного прогона, чтобы понять, что сломано, а что по-прежнему работает.
3. Разрабатываем строго по шагам. Одна задача за раз. Если в процессе работы меняются требования или архитектурные решения, сначала обновляем спецификацию, затем код.
4. Прогоняем код агентом или llm в роли архитектора-критика.
5. Каждая итерация завершается после прохождения всех quality gates. Проект в рабочем состоянии, а спецификация согласованная и соответствует коду.

## Этап 4. Деплой и наблюдаемость (Deploy & Observability)
Настраиваем:
1. Хостинг, контейнеризация
2. .
3. Тесты на этапе CD
4. Проверки безопасности (минимум секреты в коде, уязвимые библиотеки, статический анализ) 
5. Выкатку по любой из стратегий (Blue-Green / Canary / Rolling).
6. Rollback релизов, который не ломает базу данных.
7. Мониторинг ошибок, нагрузки на процессор и память.
8. Мониторинг бизнес-показателей и аналитики.
