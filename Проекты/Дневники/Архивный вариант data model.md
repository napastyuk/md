# Модель данных

Общая идея. Family Diary разделяет данные на три независимых слоя.

  

Layer 1. Evidence Layer

Свидетельства и источники

  

Corpus

↓

Artifact

↓

Fragment

↓

KnowledgeItem

  
  

Layer 2. Research Entities

Объекты исследования

  

Person

Event

Relationship

Place

Organization

  
  

Layer 3. Research Process

Инструменты для помощи в исследовании

  

ArtifactWorkflow

ResearchNote

ResearchSummary

Conflict

  

## Layer 1. Evidence Layer

Этот слой является фундаментом системы.

Главный принцип:

> Evidence Layer хранит не истину. Он хранит артефакты, фрагменты и утверждения с полностью прослеживаемым происхождением. Любой вывод в системе должен иметь возможность быть проверенным и пересмотренным.

  

### 1.1 Corpus

Назначение

Corpus — это логическая группировка артефактов.

Она используется:

- для навигации;

- для поиска;

- для группировки архивов;

- для отражения физического местонахождения материалов.

  
  

Примеры

- Домашний архив Зоткиной Ольги

- Архив семьи Ивановых

- Фотографии из деревни Михайловка

- Военные документы

  

Особенности

Corpus не владеет Artifact.

Один Artifact может находиться в `Архив семьи Ивановых` и одновременно `Военные документы`

Связь: Corpus M:N Artifact

  

Вложенность

Коллекции могут быть вложенными. Для этого нужно поле в БД `parent_corpus_id` Например:

    Архив семьи

    ├── Фотографии

    ├── Документы

    └── Дневники

  

### 1.2 Artifact

Назначение

Artifact — это реальный объект, которым владеет исследователь.

Это может быть:

- Дневник

- Фотоальбом

- Фотография

- Аудиозапись

- Видеозапись

- Письмо

- Газетная статья

- Страница сайта

- Мемуары

  

Artifact всегда представляет объект целиком. Например `Фотоальбом 1947 года` это Artifact но `Фотография №3 из альбома` это Fragment

ArtifactFile как отдельная сущность не нужен потому что файловая система уже хранит всю структуру. Например:

```

A001237/

    master/

        A001237_page_001.tif

    derivative/

        A001237_page_001.jpg

    metadata/

        checksums.sha256

```

SQLite хранит только описание Artifact. Информация о файлах вычисляется из структуры папок.

  

Поля в БД:

```sql

CREATE TABLE artifacts (

    id INTEGER PRIMARY KEY AUTOINCREMENT,  -- внутренний ключ , например 1237

    public_id TEXT NOT NULL UNIQUE,        -- публичный человеко читаемый идентификатор например A001237. Никогда не изменяется.    

    title TEXT NOT NULL,                   -- название артефакта, например Фотоальбом Ольги Андреевны  

    artifact_type TEXT NOT NULL,           -- тип артефакта, например: diary, album, photo, audio, website. Справочник можно расширять.    

    origin_type TEXT NOT NULL,             -- степень близости к первоисточнику. может быть: primary(Создан участником событий), secondary(Основан на воспоминаниях), derivative(копия, транскрипт)  

    creation_date_start TEXT,              -- дата начала создания артефакта. Используется EDTF.  

    creation_date_end TEXT,                -- дата окончания создания артефакта. Используется EDTF.            

    holder TEXT,                           -- кому сейчас принадлежит оригинал. Например: Государственный архив Волгоградской области

    reliability TEXT NOT NULL,             -- надёжность. Один из тре вариантов: low(слухи, легенды),medium(дневник, воспоминания),high(официальный документ)

    description TEXT,                      -- описание внешнего вида артефакта. Например: рукописный дневник

    filesystem_path TEXT,                  -- относительный путь файла в архиве

    created_at TEXT NOT NULL,

    updated_at TEXT NOT NULL

);

```

  

### 1.3 Fragment

Назначение

Fragment отвечает на вопрос где именно в Artifact находится информация?

Примеры:

- Страница 14

- Абзац 3

- Фотография 2

- Лицо на фотографии

- 00:12:35 - 00:13:10

  

Связь: Artifact 1:N Fragment

  

Планируемые поля в БД:

    - `fragment_type` Например: `page`, `paragraph`, `image`, `region`, `audio`, `audio_segment`, `video`, `video_segment`

    - `locator` Главное поле Fragment. Family Diary не навязывает формат locator. Он зависит от типа Fragment. Хранится как JSON.

    Например:

        - Страница: `{"page":14}`

        - Абзац: `{"page":14,"paragraph":2}`

        - Область фотографии: `{"x":100,"y":200,"w":300,"h":150}`

        - Аудио: `{"start":"01:23:45","end":"01:24:10"}`

    - `artifact_id` частью чего является цитата

    - `title` Название в свободной форме. Например: `Страница 14`

  
  

### 1.4 KnowledgeItem

Это самая важная сущность системы. KnowledgeItem — это утверждение, минимальная единица знания, извлеченная из источника или созданная исследователем.

Например: `Иван родился около 1892 года.` Это еще не доказанный факт. Это утверждение, извлеченное из источника. Главный принцип: любой KnowledgeItem должен иметь источник. То есть всегда можно построить цепочку:

`KnowledgeItem -> Fragment -> Artifact`

Важно что KnowledgeItem отделен от Person и других сущностей из Layer 2. KnowledgeItem — это цитаты и пересказы источника. Новый Person заводится вручную на со ссылкой на KnowledgeItem. Если позже утверждение окажется ошибочным (например выяснится Иван родился в другом году), KnowledgeItem помечается superseded, а Person продолжит существовать.

KnowledgeItem концептуально близок к "coded segment", "finding" или "analytic statement" в системах CAQDAS, однако дополнительно поддерживает происхождение, версионность и участие в построении генеалогических сущностей.

  

Планируемые поля в БД:

- `content` Текст утверждения. Например: Иван родился около 1892 года в Тульской губернии.

  

- `Code` связанные с KnowledgeItem один или несколько Codes.

  

- `kind` Какого рода это знание. Например:

    - сообщение/statement - автор KnowledgeItem сообщает некоторую информацию как факт.

    - наблюдение/observation - то, что непосредственно наблюдается и не требует выводов. Например: "На фотографии видно человека в военной форме"

    - цитата/quote - буквальная, дословная цитата из источника

    - мнение/opinion - оценочное, субъективное суждение автора, его мнение о чем либо. Например: "Учитель был несправедлив"

    - интерпретация/interpretation - вывод исследователя на основе других KnowledgeItem. Например: "Cемья относилась к беднейшим слоям населения"

    - гипотеза/hypothesis - предположение, которое ещё не подтверждено. Например: "Вероятно фотография сделана в период между 1905 и 1913 годами."

  

- `version` KnowledgeItem является версионным объектом. Например:

Версия 1: `KnowledgeItem.content = Фотография сделана в 1912 году`

Позже, Версия 2: `KnowledgeItem.content = Вероятнее всего между 1910 и 1913`

При этом, при добавлении новой версии, старая версия не удаляется, а помечается:

`KnowledgeItem.verification_status = superseded`

  

- `parent_id` Либо null (если это новый KnowledgeItem) либо id другого KnowledgeItem (если это исправленный KnowledgeItem)

  

- `verification_status` Жизненный цикл утверждения. Может быть одним из:

    - raw (сырой факт)

    - under_review (гипотеза)

    - confirmed (подтверждено)

    - disputed (спорно)

    - rejected (отклонено)

    - superseded (заменено или переписано)

  

- `confidence` Насколько исследователь уверен. Может быть одним из:

    - low

    - medium

    - high

  

- `date` Дата в формате Extended Date/Time Format (EDTF). Всегда timestamp диапазон.  Например: `Около 1923` хранится как

```

date_start: 1923-01-01

date_end: 1923-12-31

```

Или другой пример: `Не ранее 1923` хранится как

```

date_start: 1923-01-01

date_end: NULL

```

  

- `domain` KnowledgeItem принадлежит одному из доменов. Например:

    - family (история семьи)

    - historical_context (внешний исторический контекст)

  

- `asserted_by` заявитель или источник заявления. Тот кто утверждает то что содержится в данном утверждении. Может быть: Person, Artifact, Organization

  

- `source` список Fragment, на которых основан KnowledgeItem.

  

- `KnowledgeItemEntity` С какими сущностями второй группы выводов связано данный KnowledgeItem. Связь может быть с несколькими сущностями. Список сущностей с которыми может быть связь:

    - Персона/Person

    - Событие/Event

    - Связь/Relationship

    - Место/Place

    - Организации/Organization

  

- `research_priority` приоритет исследования. Нужно чтобы помечать незначительные события. Могут быть: low, medium, high

  

### 1.5 Code

Code инструмент аналитической классификации KnowledgeItem. Code не участвует в построении Person, Event, Place.

Code используется для:

- тематического анализа;

- поиска;

- фильтрации;

- группировки знаний;

- построения выборок.

Code может быть:

- системным;

- пользовательским.

Code может иметь поля:

- parent_code_id (коды могут быть вложенными);

- описание;

- цвет;

- aliases.

  

## Layer 2. Research Entities. Объекты исследования

Создаётся на основе Утверждений из первой группы

  

2.1 `Person` Персона - или исследовательская идентичность, объединяющая утверждения об одном и том же человеке. Весь контент персоны — это сводка всех подтвержденных и неподтвержденных утверждений к ней привязанные. Никакого "поля рождения" в персоне — только ссылка на утверждение о рождении. Но будут заметки/саммари на основе утверждений. У персоны есть поле важность: родственники, друзья и близкие знакомые, случайные знакомые

  

2.2 `Event` Событие - рождение, свадьба, переезд. Если утверждение описывает действие или изменение во времени и имеет начало или конец — создается Event. Связывает людей, места, даты. То что упоминается в утверждениях. Содержит ссылку на утверждение на основе которого был добавлен этот Event.

  

2.3 `Relationship` Связь - отношение сущностей второй группы между собой. Действует в некотором интервале времени. Например: "Костя брат Ольги" это связь Персона и Персона. Или "Ольга работала на маслобойке" это связь Персона и Организация.

Если утверждение описывает устойчивое состояние или связь создается Relationship. Есть поле

 - relationship_type. Тип справочник. Возможные значения: "родитель","работал_в","участник" и пр.

  

2.4 `Place` Место - географическая точка с историческими вариантами названия, современным аналогом и координатами и ссылками на онлайн карты. Может быть вложенным т е есть у него поле `parent_place_id`. Ефремовский уезд Тульской губернии становится конкретной точкой на карте, на которую ссылаются несколько утверждений. Дом персоны или текущий адрес организации является местом в течении какого времени. Текущий адрес организации является местом в течении какого времени.

  

2.5 `Organization` Организации - там где субъекты проводят время. Похоже на место тем что имеют координаты и историю названий, но могут иметь несколько координат(разные филиалы) и могут менять место в разное время (переезд организации). Если известно имеет дату основания и дату ликвидации.

  

Связь между сущностями: KnowledgeItem -> Event/Relationship/Place/Organization формируется на основе одного или нескольких KnowledgeItem  -> осмысляются в виде Summary

  
  

## Layer 3. Research Process. Инструменты для помощи в исследовании

Третья группа - слой моих процессов:

  

3.1 - статус конвейер/ArtifactWorkflow. Пока встреченный мною артефакт не прошел весь путь до выводов, надо где-то записывать что есть такая задача.

Содержит timestamp и текущий статус:

    1.Получен

    2.Оцифрован

    3.Размечен

    4.Выделены фрагменты

    5.Извлечены утверждения

    6.Проверен

    7.Сделаны выводы и обобщения с остальными утверждениями

  

3.2 - заметки/ResearchNote - мысли которые надо выгрузить из головы или утверждения в процессе проверки на достоверность. Может иметь связь с любой другой сущностью.

  

3.3 - Выводы/ResearchSummary - моя текстовая интерпретация на основе сущностей второй группы. Нужна чтобы видеть человеко-читаемый статус того, что уже известно. У неё есть параметр версия. При правках старые версии сохраняются с timestamp, для возможности отката. Содержит связь с на сущностями которые использовались при ее написании.

3.4 - конфликтующие данные/Conflict - там где будут автопроверки и они будут видеть несовпадение (например разные даты) будет создаваться заметка todo-шка для разрешения конфликта. Ссылается на один или несколько KnowledgeItem, которые не стыкуются между собой.
